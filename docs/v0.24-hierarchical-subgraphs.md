# v0.24 design: hierarchical subgraphs and the project DAG

Status: accepted product requirement; v0.24 implementation candidate.

Requirement provenance: this milestone comes from product-side field evidence. That
product is a validation subject, not a domain dependency. Its names, hierarchy labels,
metadata conventions, lifecycle vocabulary, governance roles, and conversion rules must
not enter DAGrail's kernel, public schema, built-in grouping logic, or default providers.
The shipped capability is a generic hierarchical DAG projection usable by any project.

## Product outcome

The default Topology view must explain the project-level DAG, not expose every runtime
mechanism at once. A high-level work unit is one collapsed group. Its assignment,
Attempts, reviews, gates, Effects, repairs, admission, publication, and later cycles stay
auditable inside that group and appear only when the user expands it or opens Execution
Detail.

Grouping is a read/projection concern. It never rewrites journal history or changes Node,
Attempt, Effect, Incident, Resource, readiness, or lifecycle semantics.

## Graph contract

Graph v1alpha1 receives two additive fields:

```yaml
spec:
  groups:
    - id: work-unit-a
      title: Work Unit A
      kind: work-unit       # work-unit | milestone | gate | external | governance | custom
      parentGroupId: phase-1
      summaryNodeId: work-unit-a-aggregate
      collapsedByDefault: true
  nodes:
    - id: work-unit-a-implement
      groupId: work-unit-a
```

Rules:

- group IDs and Node IDs occupy separate namespaces;
- `parentGroupId` must form an acyclic forest and supports at least two visible levels;
- every `groupId`, `parentGroupId`, and `summaryNodeId` must resolve in the same Graph
  revision;
- a summary Node must belong to the group or one of its descendants;
- Node dependency edges remain Node-to-Node. Groups do not become lifecycle writers or
  new dependency authority;
- active Node contracts remain frozen. Moving an active Node between groups is a view
  change only when its execution contract digest excludes `groupId`; changing its
  lifecycle inputs still requires the existing cancel/return/supersede path;
- terminal history remains append-only.

The Graph schema, Go model, patch preview/apply impact report, export, contract digest,
and compatibility tests change together. GraphPatch gains explicit `addGroup`,
`updateGroup`, `removeGroup`, and `moveNodeToGroup` operations so hierarchy changes are
previewable and revision-bound.

## Old-graph compatibility

Explicit `spec.groups` plus `node.groupId` are the only v0.24 grouping authority. An old
Graph without either remains valid and opens in the unchanged Execution Detail view.
There is deliberately no built-in metadata key, ID parser, parent-root heuristic, or
project vocabulary.

An importer, LLM skill, or compile-in provider may inspect bounded Node metadata and
propose explicit `addGroup` / `moveNodeToGroup` GraphPatch operations. The normal
preview/impact-token/apply protocol then turns the accepted proposal into GraphRevision
authority. A proposal is never silently treated as a group projection and cannot mutate
the journal from a read query. This keeps legacy conversion extensible without making
inference an invisible second authority.

## Deterministic group summary

Lifecycle and operational health are separate fields.

When `summaryNodeId` is present, the group's lifecycle summary is bound to that exact
Node runtime:

- its `planned`, `active`, `terminal`, `superseded`, or `skipped` state is preserved;
- readiness comes from the same GraphRevision frontier;
- its closed outcome and outcome class are exposed verbatim, allowing a project to show
  labels such as returned, accepted, or completed without teaching the kernel those
  words.

Without a summary Node, the fallback rollup is intentionally generic and ordered:

1. any invalid/missing child state → `unknown`;
2. any active child → `active`;
3. any ready child → `ready`;
4. any terminal failure whose dependency cut still intersects the group → `blocked`;
5. all children terminal/skipped/superseded → `completed`;
6. otherwise → `planned` or `blocked` according to computed readiness.

Operational health is calculated independently:

- unresolved Incident, unknown/failed Effect, or unclosed Resource contributes a typed
  count and changes health to `attention` or `blocked`;
- health never fabricates a lifecycle outcome;
- a group with unknown/open operational state can never be reported as cleanly
  completed;
- active Attempt count, current Attempt number/cycle, and anomaly counts are exact
  projections with bounded detail refs.

The summary report binds project ID, GraphRevision, journal head, group ID, membership
digest, summary Node ref, lifecycle summary, health, counts, and projection digest.

## Collapsed edge aggregation

For each exact Node edge, replace each endpoint with its nearest visible ancestor group.

- if both visible endpoints are equal, hide the internal edge;
- otherwise coalesce by `(visibleFrom, visibleTo, predicateKind, outcomeClass)`;
- retain an exact count, a digest of sorted source edge IDs, and a bounded inspect ref;
- expanding a group replaces only its incident aggregate edges with exact internal or
  boundary edges;
- dependency and predicate evaluation still happens on the original Node edges.

Top-level layout uses only the collapsed graph. Expanding one group appends its internal
detail without moving unrelated lane members. Five fixed generic lanes classify visible
items: work units/custom groups, milestones & gates, external actions, global governance,
and ungrouped Nodes. Associated governance Nodes appear inside their declared work-unit
group; DAGrail never guesses association from names or metadata.

## UI and API

The default tab becomes **Project DAG / Summary**. **Execution Detail** retains the exact
current topology; Operations and Timeline remain independent views. An integration may
provide a project-local label for the summary tab, but that label is not a kernel or API
term.

UI API v1beta2 adds:

- `groups[]`, deterministic group summaries, membership counts, and breadcrumbs;
- collapsed aggregate edges plus exact-edge inspect refs;
- `mode=summary|detail`, repeated `expanded=<group ID>` / `collapsed=<group ID>` values,
  group-aware search/filter results, and full top-level counts independent of the
  internal render cap;
- deep links for group or Node focus.

URL state records the selected tab, expanded group set, focus, filters, and search. The
first visit collapses all `collapsedByDefault` groups. Users can expand/collapse one,
expand/collapse all, fit the top-level graph, fit/center selection, use a minimap, and
navigate breadcrumbs. Keyboard focus, screen-reader labels, status/health legend, and
color-independent indicators cover groups and their disclosure controls.

Search is group-aware: an internal match keeps its ancestor visible, reports the number
of hidden matches, and offers expansion. The render cap applies only to displayed
internal Nodes; it never removes top-level groups or global lanes.

## Automated acceptance

Repository-neutral fixtures cover:

1. **Large project:** 58 work-unit groups and more than 1,000 internal Nodes render all
   groups in summary mode, no internal Nodes by default, and fit within the initial
   viewport model.
2. **One complex group:** one collapsed group expands to 21 lifecycle/repair Nodes and
   collapses back without changing summary, aggregate dependencies, selection, or URL.
3. **Planned work:** one group with ten predeclared internal Nodes remains one planned
   top-level item until expanded.
4. **Repair growth:** adding cycles, repair, and admission Nodes changes membership and
   health but does not increase top-level group count.
5. **Rollup safety:** open/unknown Incident, Effect, and Resource combinations never
   produce clean completed health; an explicit summary Node controls lifecycle labels.
6. **Edges:** multiple cross-group edges coalesce deterministically and recover exact
   source edges on expansion.
7. **Compatibility:** an ungrouped old Graph imports unchanged, full detail remains
   available, explicit GraphPatch conversion is revision-bound, and journal/runtime
   bytes do not change under summary/detail inspection.
8. **Accessibility/state:** keyboard disclosure, focus restoration, screen-reader names,
   deep links, reload restoration, group-aware search, and render-cap behavior have
   browser tests.

A large external project may be used as a read-only validation subject after the generic
fixtures pass. Its hierarchy names, metadata conventions, and governance Nodes must not
enter DAGrail source, schemas, fixtures, or default providers.

## Delivery sequence

1. Freeze Graph/group and UI v1beta2 schemas plus rollup/edge algorithms.
2. Implement reducer-independent group projection and GraphPatch impact validation.
3. Add summary/detail APIs, stable nested layout, disclosure state, lanes, and search.
4. Run unit, property, large-graph, browser/accessibility, compatibility, and byte-read-
   only tests.
5. Run independent cold review before commit, push, or release; only then perform the
   external read-only validation.

Non-goals: deleting internal Nodes, reducing lifecycle audit detail, replacing the
Execution Detail view, or hiding all governance work.
